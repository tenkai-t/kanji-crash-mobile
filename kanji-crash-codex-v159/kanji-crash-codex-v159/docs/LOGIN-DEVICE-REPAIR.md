# 端末の進行を維持するログイン受取記録修復（2026-11-01）

ブランチ: fix/reconcile-login-preserve-device。所有者の公開承認により、検証済みの修復機能を公開用ブランチcloudflare-testへ反映する。Cloudflareの配信切り替え完了は別途確認が必要。リモートDBの直接操作・実ユーザーの修復は未実施。修復は公開後に本人がゲーム画面で内容を確認して実行する。

## 確認できた原因と方針

所有者提供の画面で、サーバーと端末のログイン報酬受取記録の相違と、端末の所持文字・CPU段位ポイントがサーバーより進んでいることを確認。文は端末の方が少ないが、消費・報酬履歴が不明なため、差額を付与/回収しない。

所有者は「現在の端末の所持文字・段位・文を優先し、サーバーの受取履歴を維持し、報酬の二重付与なしで保存を修復する」方針に同意した。コードの実装と、実際の個人データに対する実行は区別する。

## 修復の内容

- 診断でサーバーの受取済み回数が端末より進んでいる場合だけ「端末の進行を維持して保存を修復」を表示。
- 実行前に端末/サーバーを再取得して概要を比較。ファイルバックアップの保存を案内し、既存のバックアップ保存から利用者自身に保存してもらう。ダウンロード成功をシステムが保証するものではない。
- 確認ダイアログで、維持する端末の文・所持数・段位、置き換えるサーバーの概要、既受取報酬を追加しないことを明示。キャンセル時は双方のデータを変更しない。
- 認証済み本人専用POST /api/guest/reconcile-login。既存と同じゲスト認証・ownerキー、同一オリジン制限、4MB上限を使う。
- 受け取った端末データから変更するのはloginBonusOrdinalだけ。値は実際のlogin_bonus_claimsのMAX(ordinal)に合わせる。文、かけら、所持文字、育成、編成、段位、端末のギフト履歴等は加算/減算/初期化しない。
- 既存login_bonus_claimsはINSERT/UPDATE/DELETEしない。日時・7回サイクル・当日受取済み状態は維持。過去報酬も補填しない。
- 確認時revisionと受取回数が変わったら拒否。修復前サーバーsnapshotをguest_backupsへ退避し、既存D1 batch内のCASで更新。ギフト受取履歴がサーバーにだけ存在する場合は修復を拒否して履歴を保護。
- 二重送信は同じsnapshotを確認して冪等に終了。POSTの応答消失時はGETで期待値との完全一致を確認して成功とする。
- サーバー成功後に端末へ保存し、revision/ハッシュを更新して保存保護を解除。途中で端末の内容が変わった、保存ストアが保護中、端末保存が失敗した場合は成功と表示しない。元サーバー保存は残し、元の端末データも端末の既存保存保護機構で扱う。
- 対局/召喚/マッチング中は実行しない。書込中はオーバーレイとキーボード制御で操作を防ぐ。プレイヤーID・token・復元コードは変更しない。

## 公開後、利用者が行う手順

1. ゲームを開き直す。
2. 記録 → 保存・復元 → ファイルでデータを保存・復元する → バックアップ保存。
3. 「保存が止まった理由を確認」を押す。
4. 「端末の進行を維持して保存を修復」を押し、表示される端末の文・所持数・段位を確認して承認。
5. 「修復完了」「保存済み」を確認し、ログインボーナスの「受取状況を再確認」を押す。当日受取済みなら再付与しない。翌日以降は通常の受取を使う。

表示内容に違いがある、ギフト履歴やrevisionの変更で拒否された場合は再確認する。サーバーからの無条件復元やサイトデータ削除を案内しない。
