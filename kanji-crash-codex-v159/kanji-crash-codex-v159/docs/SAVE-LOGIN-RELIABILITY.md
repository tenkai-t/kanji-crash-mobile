# サーバー保存・ログイン報酬の停止調査（2026-11-01）

ブランチ: fix/guest-save-login-reliability。所有者の公開承認により公開用ブランチcloudflare-testへ反映する。Cloudflareの配信切り替え完了は別途確認が必要。リモートDB操作は実施しない。

## 現象と確認範囲

所有者から「ログインボーナスが受け取れない」「セーブできない」、表示は「保存待ち・確認が必要」と報告された。この表示はguestBackupConflictまたはsaveRecoveryBlockedによる保護を示す。どちらの保護か、元の例外/本番の端末保存/サーバー保存の具体的な差分は未確認。保存・復元を開いて手動保存した直後の説明文を追加確認中。個人の復元コード・token・セーブは取得していない。

本番URLへのアクセスは環境のHTTP許可対象外。旧Sitesにもアクセスしない。Cloudflareの実際のテーブル・バインディング・利用上限・稼働状態を確認したとは扱わない。

## 再現した問題と修正

1. ゲスト共通通信に期限がなく、接続が応答しないと保存中/ゲスト接続確認が終わらない。20秒の中断期限（呼出元のsignalがあるときはそちら）と利用者向けのタイムアウト説明を追加。JSON以外のエラーにもHTTP番号と、413/429の説明を表示。自動で新規IDを作らない。
2. 自動保存中に手動保存すると、以前はすぐreturnしていた。ログインボーナスはその直後に保存完了を検査して失敗していた。手動保存と報酬受取は実行中の保存を待ち、その後必要な保存を行う。同時手動操作も直列化する。背景保存は従来の集約を維持。
3. PUTが確定して応答だけ失われると、端末のrevisionが古いままとなり保存競合で停止する。失敗時にGETでサーバーを読み、送信したsnapshotと完全一致するときだけrevision/ハッシュを同期する。報酬や所持品の加算はしない。通信中にローカルが変化した場合は後続保存を残す。
4. 手動保存は以前、最新revisionだけ取得して差分を見ずPUTしていた。異なるrevisionを受け入れるのは、サーバーsnapshotが現在の端末または最後に保存成功を確認したハッシュと一致する場合に限定。真の競合、報酬ordinalの不一致は引き続き保護する。
5. 端末の一時的な書込失敗でsaveRecoveryBlockedになった場合、利用者の手動保存時のみ、validSaveとsaveStore自身の保護状態を確認してwriteを再試行する。保存ストアが競合/破損保護中なら解除しない。authorizeReplacementや初期化は使わない。
6. ログイン受取前の保存に失敗した場合、一般的な「保存できません」だけでなく保存処理の具体的な説明を報酬画面に表示。
7. 保存・復元に「保存が止まった理由を確認」を追加。読取のみで端末/サーバーの文・所持数・段位ポイントを表示し、端末保護・報酬ordinal差・保存競合を区別する。保護解除、報酬付与、restore、サーバー書込は行わない。

## 追加の表示報告への対応

所有者から「サーバーに保存しています」と「保存待ち・確認が必要」が表示されるとの補足があった。この追加報告を受けた時点では、公開サイトに前回の修正自体が未反映だった。本番で同時表示に至る経路は未確定だが、従来はbusyを優先する場所と保護フラグを見る場所が分かれていた。保護中はバッジと保存ボタンの両方を「確認が必要」に統一し、busyも真の場合はボタンを無効のまま保つ。保護理由に端末保存の具体的なエラーがあれば表示する。VMテストで保護とbusyの同時成立時も「保存しています」と誤表示しないことを検証。保存保護やデータ内容はこの表示変更では操作しない。
