# 漢字クラッシュ：同時利用への改善と検証結果

2026年10月18日・公開前のレビュー用

コード修正と隔離環境での検証を実施しました。本番サイト・本番データベースは変更していません。本番で観測した実績送信400の具体的な原因は未確定です。1,000人相当の論理試験を通過しても、本番で1,000人を収容できる保証にはなりません。

## 1. 実装した変更

| 優先 | 対象 | 変更と保護する内容 |
|---|---|---|
| 1 | 使用実績の送信 | クライアントが partial:true を送る場合、正常なイベントを保存し、不正なイベントを別に返す。元のAPI呼出方法も維持する。受理されたIDだけを未送信一覧から外す。 |
| 1 | 再送の制御 | 同じ内容で拒否された記録を端末に残して自動再送を保留し、後続の正常な記録は送る。既存の「保存状況を更新」で再検証できる。保留は画面を開いている間の管理で、再読込では再検証する。 |
| 1 | 入力の検証 | items に null が混ざってもサーバー例外にせず、入力エラーとして扱う。撃破数などの従来の検証上限は維持。失敗理由を個人情報を含まないコードで区別する。 |
| 2 | 通信 | 同じプレイヤー・同じパスへの並行GETを一つにまとめ、各呼出元には独立したコピーを返す。結果を継続キャッシュせず、更新操作の前後に共有中のGETを無効化する。 |
| 2 | 対局・マッチング | ポーリングの多重起動を防ぐ。通常時の間隔は維持し、失敗時だけ再試行間隔を段階的に延長・分散する。対局の失敗時は最大5秒に抑え、既存の再接続期限は変えない。 |
| 2 | 認証 | 同じHTTPリクエスト内での重複したゲスト認証を一回にまとめる。別リクエスト・別プレイヤーには認証結果を使い回さない。 |
| 2 | ランキング | 同じWorker実行環境で重なった公開ランキング取得をまとめる。既存のD1共有ロック・30秒キャッシュを維持。非公開データを共有しない。 |
| 2 | DB検索 | 最近のオンライン対局を探すため、friend_rooms に host_key / guest_key 起点の索引を追加する移行を用意した。データの削除・書換えは含めない。 |
| 3 | 同じWi-Fi | 既存の端末IDを使い、端末別と共有IP別の両方で新規作成・復元を制限する。通常プレイは対象外。制限時は残り秒数と Retry-After を返す。 |
| 3 | フォント | 元の書体をUnicodeの範囲別に配信する。基本表示分を先に読み込み、拡張漢字はまとめた部分ファイルを必要に応じて取得する。元の一括ファイルも旧版向けに残す。 |
| 3 | 更新・診断 | 変更した資産の参照バージョンを更新。通常資産は再検証、ハッシュ付きフォントは長期キャッシュする設定を追加。APIの処理時間・状態・照合IDを確認できるようにした。 |

操作手順・ゲーム画面の遷移は変更していません。WebSocketへの移行や保存方式の変更も行っていません。

### 実績送信400の調査の限界

本番ログでは実績送信400の反復がありましたが、ログに実際のイベント内容は含まれていないため、拒否理由の特定には至っていません。
途中で検討した「復活で撃破数が4以上になる」という説明は撤回しました。落下防止は撃破の記録前に処理されており、この原因を裏付けられません。検証上限を緩める変更は取り止めています。

今回修正したのは、不正な1件による後続記録の詰まり、同じ入力の反復送信、null要素による例外です。公開後に EVENT_SHAPE_INVALID / EVENT_CHARACTER_UNKNOWN / EVENT_CHALLENGE_UNKNOWN / EVENT_COUNTER_INVALID / CPU_EVENT_INVALID / PROFILE_REQUIRED を確認し、具体的な原因を追加調査する必要があります。

## 2. 保存・ゲーム内容の維持

- インラインのゲーム処理を変更前とバイト単位で比較し、一致を確認した。
- ゲーム処理、得点、段位条件、保存保護など、保護対象のモジュールの一致を確認した。
- 保存キー、プレイヤー識別、復元コードの形式は変更していない。制限用カウンタには端末別・共有IP別の区分を追加した。
- 通常バックアップの15秒間隔、重要操作の即時保存、変更のないデータの重複送信防止、失敗時の30秒再試行、競合時の409、最新＋過去5版の履歴を維持した。
- 同じリビジョンで同時保存すると一方だけが成功し、もう一方は409となる。古いデータでの上書きは起きなかった。
- 既存SQL移行は変更していない。追加する移行は索引2本のみ。本番には未適用。

## 3. 段階試験の方法

変更前v153と修正版を別々にビルドし、同じテストコード・同じNode実行環境で順番に測定した。実プレイヤーのデータは使用せず、本番への負荷はかけていない。

Node.js 24.19.0、Worker.fetch、独立したインメモリSQLiteを使用。ネットワーク経由のCloudflare Workers/D1、実機、CDNではない。データベースは同じプロセス内で動くため、分散環境・遠隔DB待ち時間・D1の過負荷待ち行列は再現しない。

各段階で、新規プレイヤー作成、プロフィール、1人1,000体の簡略所持データの保存・取得、保存競合、マッチング、準備完了、6秒分の仮想時刻による対局ポーリング、物理処理を使った発射、発射の重複送信、時間切れ決着、結果の反復取得、ランキング取得を行った。準備変更・再接続・再戦などの分岐は別の回帰試験で確認した。

全員の新規作成を同時に開始する試験ではなく、作成後の操作を並行させたもの。IP制限はこの段階試験では付与せず、後述の共有Wi-Fi試験で別に確認した。初回ページ表示はブラウザで測っていない。

応答時間はローカルでリクエスト開始からJSON応答を読み終えるまで。CPU時間ではない。DBの数値はSQL文の実行回数であり、Cloudflareが課金する走査行数ではない。送受信量はJSON本文のみで、HTTPヘッダーや圧縮・TLSを含まない。各段階一回の参考測定で、統計的な性能保証ではない。

## 5. 継続・重複・共有Wi-Fi試験

- 50人相当で実時間60.09秒：7,200リクエスト、予期しないエラー0件。中央値3.94ms、P95 25.22ms、P99 31.46ms。SQL参照13,352回、書込1,059回、送信本文187,744B、受信本文585,275B。
- 継続試験では15秒ごとの保存と、中間時点で50人の復元・再接続を並行実行。プレイヤー間のデータ混同は検出しなかった。対局を60秒維持する試験ではなく、ランキング・招待・実績・保存系の継続試験である。
- 同じ実績IDを1,000人が各5回並行送信：5,000送信に対して台帳1,000件、文字使用回数3,000件。二重加算・他人のIDとの混同なし。
- 一部の実績が保存された後でDB失敗を模擬し、全件を再送：既に保存した分を再加算せず復旧。
- 同じIPで1,000端末の新規作成は成功し、1,001件目は429。別IPは独立して利用できた。
- 同じIPで200端末の復元は成功し、201件目は429。端末別の復元制限はIPを変更しても継続することを確認。

## 6. フォント・初回読み込み

元の通常文字フォントは4,045,744B。基本表示用の1,033文字は236,348Bに分割し、先読みする。全10,710文字の通常Unicodeマッピング・輪郭・横の文字幅を比較し、一致を確認した。補完用の元素フォントもそのまま維持する。

分割は58ファイルで、全体を取得すると4,720,360Bとなる。元の一括版より総量は増えるため、全種類を表示する状況では通信件数・合計量が増えるという交換条件がある。必要な範囲だけ取得し、ハッシュ付きファイルを長期キャッシュする設計。初回の全通信量が236KBになるという意味ではない。

実ブラウザでの転送量、フォント切替時の見え方、CDN圧縮・キャッシュヘッダーの実際の反映は未確認。JavaScript・画像の削除や演出の簡略化はしていない。

- Workers標準：月額最低5米ドル、月1,000万リクエストとCPU 3,000万msを含む。超過は100万リクエストあたり0.30ドル、CPU 100万msあたり0.02ドル。

- 無料枠ではWorkersが1日10万リクエスト、D1が1日500万読取行・10万書込行。標準の単一DBには処理待ち行列の制約があり、ローカル試験だけでは余裕を判定できない。

## 9. 公開後の確認と戻し方

現時点で本番への公開はしていない。公開を承認した場合は、保存済みの同じソースと配信アーカイブを使用する。

1. 公開前に本番の直近エラー件数とAPI応答を記録し、DB索引追加の適用結果を確認する。移行にはデータ削除を含めない。
2. 公開直後は少人数で作成・復元・対戦・保存・ランキングを確認し、保存失敗や混同があれば拡大を止める。
3. kanji-api ログからルート別の4xx/5xxと処理時間を確認する。失敗は全件、成功は約1％を記録するため、成功ログだけで総件数を数えない。Server-Timing と X-Kanji-Request-Id で照合できる。復元コード、トークン、所持データ、プレイヤーID、部屋コード、クエリはログに含めない。
4. 実績送信は play-progress-validation の分類コードを確認する。正当な記録の拒否が判明した場合は、その互換性を保って修正し、保留した記録を手動再検証する。記録の削除で解決しない。
5. 429の増加、5xxの継続、保存・復元の異常があれば直前のv153へ戻す。新索引は残っていても旧コードは利用可能。プレイヤーの保存内容・認証形式は旧版と互換で、DBデータを巻き戻す必要はない。部分受理された実績は従来のID台帳で重複を防ぐ。元の一括フォントも残している。
6. 実サーバーでの50→100→200人の段階試験を別途計画する。上限・中止条件・費用を提示し、了承後に実施する。今回のローカル結果を本番の収容人数として宣伝しない。
